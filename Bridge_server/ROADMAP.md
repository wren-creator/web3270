# Roadmap

## Graphics
- [x] Arcs — `tn3270/gddm.js` now decodes Set Arc Parameters (X'22'), three-point Arc (X'C6'), and Full Arc (X'C7') per the GDDM Base Programming Reference (Appendix D), and `public/js/gddm.js` renders circles/ellipses via a canvas transform + circumcircle geometry for the three-point form. `mock-lpar.js`'s `GDDM` demo now exercises both. The "at current position" short forms (X'86'/X'87') are intentionally skipped, same as the existing GCHST-at-current-position handling — this decoder doesn't track current position across orders.
- [x] Fillets — `tn3270/gddm.js` now decodes the Fillet order (X'C5', a polyfillet of 2+ points). `public/js/gddm.js` renders it as a series of quadratic Bezier pieces through consecutive segment midpoints, which exactly satisfies the manual's tangency rule (curve tangent to the first/last line at their endpoints, tangent to intermediate lines at their midpoints) and its two special cases (2 points → straight line, 3 points → a single smooth arc). `mock-lpar.js`'s `GDDM` demo now draws a 5-point decorative ribbon to exercise the multi-piece case.
- [x] Character sets — `tn3270/gddm.js` now decodes the Character Set order (X'38'). Per the 3270 Data Stream Programmer's Reference (GA23-0059), the Object Data structured field's OBJTYP has no value for transmitting symbol-set glyph data at all (only Graphics X'00' and Image X'01' exist), so a symbol set is necessarily a client-resident resource, like a built-in font, not something sent over the wire — the decoder just passes the selected LCID through with the character string. `public/js/gddm.js` owns the actual glyph table (`VECTOR_SYMBOL_SETS`), currently one hand-authored 7-segment-style digit set (LCID X'41'), rendered as independent line strokes at a fixed pixel size next to regular labels. `mock-lpar.js`'s `GDDM` demo now shows a "TOTAL" readout whose digits render through this custom font, visibly distinct from the default browser-font text everywhere else on the same screen.
- [x] Images — `tn3270/gddm.js` now decodes the Begin Image (X'D1', FORMAT 0 only) / Image Data (X'92') / End Image (X'93') sequence: a monochrome bitmap, 1 bit per display point, one row per Image Data order. Verified byte-for-byte against the manual's own worked example (a 9x4 hollow square). `public/js/gddm.js` rasterizes the packed bits onto an offscreen canvas in the current color, then scales it into place with image smoothing off for a crisp pixel-art look. The manual doesn't state row order or which corner the position anchors — this renderer's documented, reasoned interpretation is top-to-bottom rows anchored at the bottom-left corner (ordinary raster convention). `mock-lpar.js`'s `GDDM` demo now draws a hand-encoded 8x8 up-arrow icon, scaled up in the corner. **Correction:** every image primitive was actually invisible in the browser until now. Each row was stored as a Node `Buffer`, which crosses a `JSON.stringify` boundary (`utils/send.js`) on its way to the client; `Buffer` serializes there as `{type:'Buffer',data:[...]}`, silently breaking the renderer's `row[c>>3]` indexing (every lookup came back `undefined`, so no pixel ever got painted). Fixed by storing rows as plain arrays in the decoder. Verified in-browser (Playwright against a rebuilt Docker stack): the up-arrow icon now renders with real opaque pixels.
- [x] Color-mix modes — `tn3270/gddm.js` now decodes the Color Mix order (X'0C', short format), the AS/400 GDDM Reference's Appendix B "Color Mix Order" (GSMIX): default, mix (OR), overpaint, underpaint, exclusive OR. `public/js/gddm.js` maps each mode to the closest real `globalCompositeOperation` — overpaint is ordinary drawing, underpaint maps exactly to `destination-over` (old color wins where both are set), xor has a direct canvas match, and mix (OR) uses `lighter` as the nearest analog since canvas has no literal OR blend. `mock-lpar.js`'s `GDDM` demo now draws four pairs of overlapping filled squares, one pair per mode, below the chart's x-axis (verified rendering correctly distinct per mode via Playwright screenshots against a rebuilt Docker stack). Clipping is intentionally NOT implemented: the manual's Appendix B GDF order list is alphabetical and has no Clip order at all (nothing sorts between "Character Shear" and "Color" where one would land) — `GSCLP` is a host-side GDDM API call that shapes what the mainframe puts in the GDF stream before it's ever sent, so there's nothing on the wire for a terminal-side decoder to act on. This closes out full GDF order-set coverage for the non-segment, non-shading-pattern orders.
- [x] Hidden `USA` easter egg — a WarGames/WOPR nod. Typing `USA` at the TSO READY prompt (or from the TSO command shell) brings up a "GLOBAL THERMONUCLEAR WAR" screen: a stylized continental-US outline (Line order) and a fan of curved trajectory arcs (Arc order) radiating from a central launch-site marker out past the picture boundary, all built entirely from the GDF orders this engine now supports. Same TSO-command-triggered pattern as the `GDDM` demo (`mock-lpar.js`'s `screenUSA`/`buildUsaObjectDataWsf`).

## 3270 Datastream
Issues flagged on web3270#19 (the field color/highlight propagation bug, fixed).
- [x] ISPF partial-update screen corruption — web3270#19, reported by racingmars. ISPF rarely erases between panels, it relies on partial writes that reuse buffer addresses. `_processWriteCommand`'s plain-character and RA (Repeat to Address) branches mutated the existing buffer cell in place and only ever touched `.char`, so a stale `.fa` (and its stashed SFE color/highlight) from an earlier field attribute byte at that address stuck around forever once the host reused the position for plain content. `_bufferToRows`/`_extractFields` both key off `cell.fa !== undefined` to find field boundaries, so every stale cell became a phantom field, splitting real fields and corrupting the color/highlight forward pass at the wrong spot, exactly matching his screenshots and the field desync he saw when typing. Verified against his own captured wire log (login → ISPF → "3.4" DSList panel): before the fix, that panel's partial write left 1,541 cells with stale `.fa` and `_extractFields()` returned 260 fields (204 phantom); after, 0 stale cells and 149 fields, exactly matching the 149 real field-attribute bytes, with the rendered panel matching real ISPF line for line. Fixed in `fix/pipe-render-font`; both branches now clear `.fa`/color/highlight unconditionally on write. Racingmars's own suggested fix (a single forward pass recomputing display attributes at EOR) was already in place from the earlier color-propagation fix — this bug was upstream of that, in the buffer mutation itself.
- [ ] Graphic Escape / codepage 310 support — `tn3270/session.js`'s `ORDER_GE` handler just skips the next byte (`i += 2`) instead of decoding it. Root cause confirmed for why go3270's example1 status bar (green/yellow/red graphics characters) never renders. Needs a codepage 310 (graphics/symbol) table plus real GE decoding in the datastream parser.
- [ ] Vertical pipe `|` not rendering — web3270#21. Data path proven clean: replayed the reporter's own captured wire log through the real `_handle3270Record`/`_bufferToRows` code and every EBCDIC `0x4F` decodes to `|` correctly; traced the rest of the pipeline (emit → WS JSON → `renderLiveScreen()`) by hand with nothing found. Leading theory is the CDN-loaded IBM Plex Mono/Sans (`fonts.googleapis.com`) silently failing on the reporter's network-restricted VM and falling back to a bare `monospace` keyword — both his browsers (Firefox, Chromium) showed identical behavior, consistent with a shared substituted font. `fix/pipe-render-font` self-hosts the fonts and drops the CDN dependency entirely; verified via Playwright that pipes render correctly against the self-hosted font, but unconfirmed against the reporter's actual failure — waiting on him to test the branch or supply devtools confirmation.

Column positions for both spec types were pulled from IBM's own ILE RPG Language Reference (SC09-2508) and the DDS Reference: Display Files manual via `pdftotext`, not reconstructed from memory, matching this project's existing byte-level-verification convention for the 5250 datastream itself. Architecture note: `EXFMT` (write a format, then read it) maps onto a JS generator that yields the format to render and resumes via `.next({key, values})` on the next AID key, which is what lets a running program's state live entirely outside the daemon's `screen` state machine as just one more screen value (`RPG_RUN`). Supported opcode subset: `EVAL`, `IF/ELSE/ENDIF`, `DOW/ENDDO/LEAVE`, `SELECT/WHEN/OTHER/ENDSL`, `EXSR/BEGSR/ENDSR`, `EXFMT`, `DIV/MVR`, `RETURN`. Random rolls deliberately use classic `DIV`/`MVR` for modulo rather than a compound `EVAL` expression, since RPG has no `%REM` until well past V4R3 (the real hardware target for this feature) and intermediate-expression truncation inside one `EVAL` isn't unambiguous real RPG behavior. Caught and fixed a real bug along the way: the expression evaluator's `AND`/`OR` handling used JS's short-circuiting `&&`/`||`, which skipped *parsing* (not just evaluating) the right-hand operand whenever the left side was already decisive, leaving unconsumed tokens and throwing — now both sides are always parsed regardless of the short-circuit value. See `mock-lpar/README.md`'s "A real RPG interpreter" section for the full architecture writeup.
